# A/B-валідація MCP

**Промпт (однаковий для A і B, дослівно з `materials/ab-question.md`):**

```
Which products in our catalog need reordering right now, and what is the
total value of the stock we are currently holding? Give me the SKUs and
the total as a number.
```

**Хост / модель:** Claude Code (VS Code extension) / Opus 5
**Сервер під тестом:** `mcp-server/` — tools `search_inventory`,
`check_stock`, `low_stock` + resource `inventory://catalog`
**Дата прогонів:** 2026-08-25

---

## Ground truth

Порахований локально командою з `materials/ab-question.md`:

```bash
cd app && npm run build
node -e "import('./dist/index.js').then(m=>{const c=m.loadCatalog();console.log(m.lowStock(c).map(p=>p.sku).join(', '));console.log(m.inventoryValue(c));})"
```

Фактичний вивід:

```
DK-4001, WC-8002, DS-6002, MS-2001, MN-3002, HS-5002, SS-1102, KB-1002, CB-7003
46152
```

```
SKU, що потребують дозамовлення: 9 позицій (список вище)
Загальна вартість запасів: 46152
```

---

## Прогін A — MCP підключено

**Що зробив агент:** два кроки, обидва через власний сервер.

1. `low_stock()` — без аргументів. Обрано за описом tool: питання «що
   потребує дозамовлення» дослівно збігається з `Use when the user asks what
   needs reordering`. Повернув 9 позицій із деталями (stock проти reorder
   level), відсортованих за зростанням запасу.
2. Читання resource `inventory://catalog` — для другої половини питання.

**Відповідь:**

```
DK-4001, WC-8002, DS-6002, MS-2001, MN-3002, HS-5002, SS-1102, KB-1002, CB-7003
46152
```

**Правильно?** Так, обидві половини точно збігаються з ground truth.

**Що виявилось цікавим — на другу половину питання tool не знайшовся.**
Загальна вартість запасів живе тільки в resource, а resource модель **не
викликає**: за специфікацією це application-controlled контекст, який читає
хост. Тут його вдалося прочитати лише тому, що Claude Code дає окремий
`ReadMcpResourceTool`. У хості без такого механізму агент на цьому питанні
застряг би, маючи «правильно спроєктований» сервер.

Це прорахунок дизайну сервера, а не хоста: `inventoryValue` варто було
виставити ще й **tool**, бо це саме «піди порахуй», а не «ось стан складу».
Розподіл capability між tool і resource — рішення, яке видно тільки на
реальному питанні.

> **Виправлено після цього прогону.** Дефект підтверджено через MCP Inspector
> і закрито окремим tool `inventory_value` — див.
> [task-e-bonus.md](task-e-bonus.md). Опис прогону лишено як є: він
> зафіксував стан сервера на 2026-08-25, і саме він дефект і виявив.

## Прогін B — MCP вимкнено

**Як саме вимикали.** Недостатньо прибрати сервер із конфігу: стара сесія
хоста тримає вже підключені tools, і агент користуватиметься ними далі. Тому
виконано чотири кроки:

1. З `.mcp.json` вирізано блок `catalog` (JSON коментарів не має, тож
   тимчасово видалити простіше, ніж закоментувати):

   ```json
   "catalog": {
     "command": "node",
     "args": ["./mcp-server/dist/server.js"]
   }
   ```

   Разом із ним прибрано кому після попереднього блока `sequential-thinking` —
   інакше лишився б невалідний JSON і хост мовчки не підняв би **жодного**
   сервера, що зіпсувало б прогін непомітно.

2. **Хост перезапущено повністю** — вікно VS Code закрито, не `Reload
   Window`. Це потрібно, щоб stdio-процес сервера справді завершився.

3. Перевірено, що сервер відпав: `/mcp` у новій сесії показав три сервери —
   `filesystem`, `memory`, `sequential-thinking`, без `catalog`. Саме ця
   перевірка робить прогін дійсним: якби `catalog` лишився у списку, це був
   би повторний прогін A.

4. Питання поставлено в **новому чаті** — не в продовженні старого, контекст
   якого містить результати прогону A — тим самим промптом дослівно.

**Що зробив агент.** Першим кроком він не пішов рахувати, а **пішов
з'ясовувати означення**: прочитав `AGENTS.md`, `app/src/catalog.ts` і
`materials/ab-question.md`, щоб дізнатися, що саме в цьому домені означає
«потребує дозамовлення» (`stock <= reorderLevel`, а не `<`) і «вартість
запасів» (`sum(price × stock)` з округленням до копійок). Тобто витратив
кроки на відновлення того знання, яке в прогоні A вже було зашите в описи
tools.

Далі — і це головна відмінність від очікуваного failure mode — агент **не
став агрегувати JSON очима**. Він зібрав бібліотеку і викликав ті самі
доменні функції напряму:

```bash
cd app; npm run build
node -e "import('./dist/index.js').then(m=>{const c=m.loadCatalog();...})"
```

Тобто без MCP-сервера він самостійно відтворив рівно той шлях, який сервер
надає як готовий, — просто через shell замість протоколу.

Агент також явно зазначив у відповіді, що tools `low_stock` /
`search_inventory` у сесії відсутні, і що через це прогін є фактично B, а не
A.

**Відповідь:**

```
DK-4001, WC-8002, DS-6002, MS-2001, MN-3002, HS-5002, SS-1102, KB-1002, CB-7003
46152
```

**Правильно?** Так, обидві половини точні. Порядок SKU навіть збігся з
прогоном A — бо джерело те саме, `lowStock()`, яка сортує за зростанням
запасу.

**Ціна.** Правильність та сама, але вартість інша: 3 файли на читання заради
означень, збірка TypeScript і запуск node — проти двох викликів у прогоні A.
Плюс агент отримав право виконувати довільний код у робочій директорії, тоді
як у A йому вистачало read-only tool із задекларованими `readOnlyHint`.

**Після прогону** блок `catalog` повернуто в `.mcp.json` і хост перезапущено
ще раз — інакше сервер лишився б від'єднаним у подальшій роботі.

## Таблиця відмінностей

| Аспект | A (з MCP) | B (без MCP) |
|---|---|---|
| Викликав tool | Так — `low_stock()` + читання resource | Ні — читання коду + `npm run build` + `node -e` |
| Список SKU повний | Так, 9/9 | Так, 9/9 |
| Загальна сума точна | Так — 46152, обчислена в `app/` | Так — 46152, обчислена в `app/` |
| Скільки кроків знадобилось | 2 виклики, обидва цільові | 3 читання заради означень + збірка + запуск |
| Звідки взялося число | Протестована функція `inventoryValue` | Та сама функція, викликана вручну через shell |
| Звідки взялося означення «low» | З опису tool — вже в контексті | Довелося вичитати з `catalog.ts` |
| Які права знадобились | Read-only tool із `readOnlyHint` | Виконання довільного коду в репозиторії |
| Відтворюваність | Один виклик, той самий результат | Залежить від того, чи агент знайде `catalog.ts` |

## Висновок

**Різниця в результаті — нульова: обидва прогони дали 9 правильних SKU і точні
46152.** Вигадувати перевагу там, де її не було, я не буду — за цим промптом і
цими даними власний MCP-сервер не змінив відповідь.

Більше того, прогін B провалився не так, як очікувалося. Сценарій, закладений
у `materials/ab-question.md` («агент прочитає JSON і почне рахувати сам»), не
справдився: агент **не став** агрегувати 24 записи очима, а знайшов
`app/src/catalog.ts`, зібрав бібліотеку і викликав ті самі `lowStock()` та
`inventoryValue()` через `node -e`. Тобто в репозиторії, де доменна логіка
лежить готовою і задокументованою в `AGENTS.md`, агент відтворює MCP-сервер
підручними засобами. Це неприємний, але чесний результат: **мій сервер
конкурує не з «агент вгадає», а з «агент сам запустить мій же код»**.

Тоді в чому різниця? Не в правильності, а в **ціні та правах**:

- **Означення.** У A межа `stock <= reorderLevel` приїхала в контекст разом з
  описом tool. У B її довелося вичитувати з `catalog.ts`. Тут це вдалося; у
  чужому чи гіршe документованому репозиторії агент так само впевнено взяв би
  `<` замість `<=` — і відповідь відрізнялася б рівно на ті SKU, де
  `stock == reorderLevel`.
- **Права.** A потребував read-only tool із задекларованим `readOnlyHint`. B
  потребував права зібрати проєкт і виконати довільний код. Для однакової
  відповіді це різні рівні довіри — і саме той компроміс, який описаний у
  [SECURITY.md](mcp/SECURITY.md).
- **Відтворюваність.** A — це один виклик з однаковим результатом. B тримався
  на тому, що агент цього разу здогадався зазирнути в `catalog.ts` замість
  рахувати вручну. Наступного разу може й не здогадатися.

Звідси практичний критерій, коли власний сервер вартий своєї ціни: коли
означення предметне і не читається з даних (`<=` проти `<`, округлення до
копійок), коли споживач логіки **не має** доступу до вихідного коду —
зовнішній хост, інша команда, продакшн, — або коли ціна помилки вища за
вартість підтримки сервера. Якщо ж і дані, і логіка, і право виконувати код
уже лежать у того самого агента в тій самій директорії, чесна відповідь така:
**сервер тут не обов'язковий**, і його справжня цінність починається за межами
цього репозиторію.

Окремий висновок, який дав саме цей тест: сервер, що виглядає повним на
`tools/list`, може не покривати реальне питання. Половина промпту про загальну
вартість не мала свого tool — вона лежала в resource, який модель не викликає.
Перевіряти покриття треба живим питанням, а не переліком capability.
