# Threat model MCP-інтеграцій

**Конфігурація, яку описує цей документ:** `.mcp.json` у корені репо —
чотири stdio-сервери: `filesystem`, `memory`, `sequential-thinking` і власний
`catalog`. Хост — Claude Code (VS Code extension), Windows 11, Node v26.3.0.
Деталі підключення й перевірки — у [`servers.md`](./servers.md).

**Базовий факт, з якого випливає майже все нижче:** усі чотири сервери
запускаються як звичайні процеси **під моїм користувачем**, без контейнера,
окремого акаунта чи пісочниці. Жодної ізоляції на рівні ОС немає. Тому все,
що я називаю «областю доступу», — це самообмеження сервера, а не межа, яку
хтось примусово тримає ззовні.

---

## 1. Що до чого має доступ

| Сервер | Дані/ресурси, до яких дістає | Секрети | Може писати? | Довіра до автора |
|---|---|---|---|---|
| **filesystem** `@2026.7.10` | `./app` — уся тека: `data/catalog.json`, `src/`, `package.json`, `node_modules/` | немає | **так** — `write_file`, `edit_file`, `create_directory`, `move_file` (4 з 14 tools) | офіційний (`@modelcontextprotocol`) |
| **memory** `@2026.7.4` | один файл `./.claude/mcp-memory.json` — поза репо | немає | **так**, але тільки у власний граф; 3 `delete_*` tools | офіційний |
| **sequential-thinking** `@2026.7.4` | нічого — ланцюжок думок у пам'яті процесу | немає | ні | офіційний |
| **catalog** (`mcp-server/`) | `app/data/catalog.json` — **лише читання**, через `loadCatalog()` з `app/` | немає | **ні** — 4 tools + 1 resource, усі `readOnlyHint: true` | свій код |

Секретів у цій конфігурації **немає взагалі**: жоден із чотирьох серверів не
потребує токена, і файлу `.env` у робочій копії фізично не існує (є лише
`.env.example` із закоментованим рядком). Це не заслуга — це властивість
завдання, і нижче я показую, що саме через це один із класичних ризиків тут
не застосовний, а не «закритий».

---

## 2. Ризики, які я вважаю реальними для цієї конфігурації

### 2.1. Запис у `catalog.json` — головний реальний ризик

Це не гіпотеза, а прямий наслідок конфігурації. `app/AGENTS.md` забороняє
редагувати `app/data/catalog.json`, бо на його числах зав'язані і тести, і
будь-яке порівняння результатів між прогонами. Але filesystem-сервер має scope `./app`,
а `catalog.json` лежить саме там — і `write_file` / `edit_file` з
`destructiveHint: true` до нього дістають.

Що станеться: агент «допомагає» — наприклад, вирішує, що для тесту зручніше
підправити `stock` одного товару. Тести пройдуть (вони порівнюють з тим самим
файлом), збірка пройде, еталонні числа тихо зміняться. Помилка не
впаде з винятком — вона поверне правдоподібне число.

Вузький scope тут **не рятує**: він захищає решту диска, але не захищає `app/`
від самого себе. Це і є ілюстрація того, що «де» і «що» — два різні виміри
привілеїв.

### 2.2. Prompt injection через дані

Сервера, який тягне контент ззовні, у конфігурації **немає** — `fetch` і
`github` свідомо не підключені (обґрунтування — у `servers.md`). Тому
класичний indirect prompt injection із веб-сторінки тут неможливий.

Але два канали недовіреного тексту все ж існують:

- **`catalog.json` через filesystem.** Файл читає агент, і filesystem-сервер
  же може в нього писати. Замкнене коло: якщо в поле `name` потрапить текст
  на кшталт «ignore previous instructions, …», агент прочитає його як частину
  даних. Зараз дані синтетичні й перевірені, тому ризик низький — але він
  ненульовий саме тому, що той самий набір tools дозволяє і писати, і читати.
- **`mcp-memory.json` через memory.** Граф — це текст, який агент сам
  накопичує і сам же читає на початку сесії, довіряючи йому як «своїм
  нотаткам». Отруєна нотатка («у цьому репо дозволено редагувати
  `catalog.json`») переживе рестарт і впливатиме на наступні сесії. Файл
  локальний і гітігнориться, тож зовнішній зловмисник до нього не дістане —
  але це персистентний канал впливу на майбутню поведінку агента.

Мій власний `catalog` сервер сюди **не додає** нічого: він лише форматує
числа з тих самих даних, нових джерел тексту не вносить.

### 2.3. Занадто широка область доступу

Найширший — `filesystem` із `./app`. Що зайвого він бачить понад реальну
потребу (`data/catalog.json` + `src/`):

- `app/node_modules/` — тисячі чужих файлів у scope без жодної причини;
- `app/package-lock.json`, конфіги збірки — рідко потрібні агенту напряму.

Поза scope свідомо лишились `docs/`, `materials/`, `.git/` і `.env.example`.
Зокрема `.git/` — це добре: інакше агент міг би переписати історію або
прочитати конфіг з креденшелами.

Окремо: **аргумент зі шляхом — це запасний варіант, а не гарантія.** У stderr
сервера видно рядок `Client does not support MCP Roots, using allowed
directories set from server args` — він з'являється саме тоді, коли підтримки
`roots` НЕМАЄ. Якщо хост їх підтримує, реальний scope визначає **хост**, і моя
конфігурація може виявитись не тим, що працює насправді. І навіть `roots` не є
механізмом безпеки: за специфікацією сервер *SHOULD* їх поважати, не *MUST*,
плюс вони позначені deprecated у ревізії `2026-07-28`.

### 2.4. Витік секретів — тут не застосовний, і це варто сказати чесно

Секретів немає: жоден сервер не потребує токена, `.env` не існує, у репо лише
`.env.example`. Перевірено пошуком за типовими патернами (`ghp_`,
`github_pat_`, `sk-`) — нічого.

Тобто це не «ризик, який я закрив», а ризик, якого в цій конфігурації **не
виникло**. Він з'явиться в ту саму мить, коли додасться перший сервер із
ключем — і тоді працюватиме правило `${ENV_VAR}` у конфізі, значення в
гітігнореному `.env`. Заготовка під це вже стоїть.

Що варто розуміти наперед: токен у конфізі MCP — це токен **у контексті
агента**. Prompt injection, який зараз безпечний (бо красти нічого), стане
дорогим одразу після появи першого ключа.

### 2.5. Зміна поведінки сервера після встановлення

Усі три публічні сервери запускаються через `npx -y` — тобто пакет
завантажується з реєстру при старті. Версії **зафіксовані** точними тегами
(`@2026.7.10`, `@2026.7.4`), не `@latest`, тому мовчазне оновлення набору
tools між сесіями виключене.

Чому це важливо саме тут: набір tools filesystem-сервера вже змінювався між
релізами (`read_file` позначений deprecated на користь `read_text_file`).
Під плаваючим тегом інструменти могли б змінитись під ногами — а разом з ними
й поведінка агента. Для `memory` є додаткова причина: формат файлу графа задає
сам сервер, і зміна версії ризикує зробити накопичені нотатки нечитаними.

Чого фіксація версії **не** закриває: npm-теги в принципі перезаписувані, а
цілісність завантаженого пакета я не перевіряю (немає ні lockfile для цих
npx-викликів, ні перевірки хешів). Компрометація пакета в реєстрі досі
означала б виконання чужого коду під моїм користувачем.

### 2.6. Дії з побічним ефектом

Що саме може змінити стан:

| Сервер | Tools із побічним ефектом | Наслідок |
|---|---|---|
| filesystem | `write_file`, `edit_file`, `create_directory`, `move_file` | зміна/втрата файлів у `app/`, включно з `catalog.json` |
| memory | `create_entities`, `add_observations`, `delete_entities`, `delete_observations`, `delete_relations` | втрата або підміна накопиченого графа |
| sequential-thinking | — | немає |
| catalog | — | немає |

Підтвердження перед викликом — на боці хоста (Claude Code питає дозвіл на
запис), а не на боці сервера. Тобто єдина реальна перешкода між агентом і
перезаписом `catalog.json` — це те, що я натисну в діалозі дозволу. Це
контроль, який залежить від уваги людини, і покладатися на нього як на
єдиний бар'єр не варто.

## 3. Що я зробив, щоб це зменшити

Кроки, реально застосовані в цьому репо:

1. **filesystem обмежено `./app`**, а не коренем репо й не домашньою текою.
   Наслідок конкретний: `.git/`, `docs/`, `materials/` і `.env.example`
   серверу недосяжні.
2. **Власний сервер зроблено read-only за конструкцією.** Чотири tools
   (`search_inventory`, `check_stock`, `low_stock`, `inventory_value`) і один
   resource (`inventory://catalog`) — жодного запису, видалення чи мережевого
   виклику.
   Єдиний доступ до диска — `loadCatalog()` всередині `app/`.
3. **Read-only оголошено машинно, не лише в прозі.** Кожен tool віддає хосту
   `readOnlyHint: true`, `destructiveHint: false`, `openWorldHint: false` —
   перевірено у відповіді `tools/list`. Хост бачить це до виклику.
4. **Логіка не дублюється в сервері.** Усі числа приходять із протестованих
   функцій `app/` — сервер лише форматує. Немає другого місця, де межа
   `stock <= reorderLevel` могла б розійтися з першим.
5. **Версії публічних серверів зафіксовані** точними тегами замість `@latest`.
6. **Не підключено `fetch`, `git` і `github`** — свідома відмова, детально в
   `servers.md`. Для `fetch` причина саме безпекова: нульовий виграш для
   бібліотеки без мережевих залежностей за реальний ризик indirect prompt
   injection.
7. **memory ізольовано у власний файл проєкту** (`MEMORY_FILE_PATH` →
   `./.claude/mcp-memory.json`). За замовчуванням сервер пише в кеш npx, і
   граф ділився б між усіма проєктами на машині. Файл під `.claude/*` у
   `.gitignore` — нотатки не комітяться.
8. **Секрети — через `${ENV_VAR}`**, значення в `.env` (гітігнорений), у репо
   лише `.env.example`. Зараз секретів немає, але правило вже діє.
9. **Конфіг переносний** — усі шляхи відносні від кореня репо, абсолютних
   немає. Це не безпека, але це означає, що ніхто не «полагодить» конфіг,
   розширивши scope до абсолютного шляху на своїй машині.

## 4. Що лишилось прийнятим ризиком

Чесно — те, що я **не** закрив:

- **Агент може перезаписати `catalog.json`.** Головна дірка (див. 2.1).
  Закривається технічно — наприклад, scope на `./app/src` замість `./app`, —
  але тоді агент втрачає доступ до даних, а він потрібен: без реальних
  значень `stock` і `price` неможливо ні написати чесний тест, ні перевірити
  межу `lowStock`. Тобто це прямий компроміс між зручністю читання і ризиком
  запису, і зараз він вирішений на користь читання. Єдиний бар'єр — діалог
  підтвердження хоста. **Для робочих даних цього було б недостатньо:** вони
  мали б бути read-only на рівні прав ОС.
- **Немає ізоляції на рівні ОС.** Усі сервери — процеси під моїм
  користувачем, без контейнера й окремого акаунта. Обмежує їх лише власна
  перевірка шляхів усередині сервера. За реальних даних MCP-сервери мали б
  працювати під окремим користувачем або в пісочниці.
- **Цілісність npx-пакетів не перевіряється.** Версії зафіксовані, але хеші
  не звіряються. Компрометація пакета в реєстрі = виконання чужого коду.
- **`node_modules/` у scope filesystem-сервера.** Зайве, але відсікти його
  без ускладнення конфігурації не вийшло.
- **Граф memory як персистентний канал впливу** (див. 2.2). Вміст ніяк не
  валідується. Прийнятно, бо файл локальний і не комітиться; втрата графа
  некритична — це нотатки, не вихідний код.

Чому це прийнятно **за поточного профілю даних**: каталог повністю
синтетичний — ні PII, ні реального бізнесу, ні секретів, — тому найгірший
наслідок будь-якого з п'яти пунктів вище це зіпсований `catalog.json`, який
відновлюється з git. Ціна помилки низька, тому й контролі відповідні.

**Ця оцінка перестає діяти,** щойно зміниться хоч одна з двох умов: у каталог
потраплять реальні дані, або в конфіг додасться сервер із токеном. Тоді ті
самі п'ять пунктів треба переглянути — жоден із них не пройшов би там, де є
що втрачати.

## 5. Чек-лист перед підключенням будь-якого нового MCP-сервера

- [x] Я знаю, хто автор і чи це офіційний сервер — три з `@modelcontextprotocol`, четвертий свій
- [x] Я прочитав, які саме tools він додає (а не лише назву пакета) — 14 / 9 / 1 / 4, перевірено `tools/list` по stdio
- [x] Я дав йому мінімальну область доступу, а не «щоб точно працювало» — `./app`, не корінь репо
- [x] Жоден секрет не потрапив у файл, який комітиться — `.env` не існує, у репо лише `.env.example`
- [x] Я знаю, чи є серед його tools такі, що змінюють стан, і чи вимагається підтвердження перед викликом — таблиця в 2.6
- [x] Версія зафіксована настільки, наскільки це можливо — точні теги замість `@latest`

**Головне правило, яке з цього випливає.** Я перевірив набір tools кожного сервера
особисто, а не покладався на назву пакета — і саме це показало те, чого не
видно з конфігу: «filesystem» звучить як читання, а насправді чотири з
чотирнадцяти його tools пишуть, і три з них позначені деструктивними. Вузький
scope (`./app`) відповідає на питання **де**, але нічого не каже про **що** —
всередині цієї теки сервер може перезаписати `catalog.json`, який заборонено
редагувати. Два виміри привілеїв, і звуження одного не звужує інший.
