# MCP-сервери проєкту

**Хост(и), у якому налаштовано:** Claude Code (VS Code extension)
**Файл конфігурації:** `.mcp.json` у корені репозиторію (project scope —
призначений для команди, тому закомічений)

> **Переносимість.** Усі шляхи в конфізі — відносні від кореня репозиторію,
> команда одна (`npx`), абсолютних шляхів немає. Тому файл працює на будь-якій
> машині з Node без правок; конкретні шляхи в цьому документі, де вони
> потрібні для ілюстрації, замінено на `<REPO>`.
>
> Перевірено на: Windows 11, Node v26.3.0. Єдина вимога — Node 22+ (як і для
> самого `app/`).

> `uv` / `uvx` у цьому середовищі **не встановлено**. Оскільки проєкт цілком
> на Node, взято три npx-сервери — вони працюють на вже наявному тулчейні й не
> додають другої мовної залежності лише заради інструментів розробки.

## Сервер 1 — filesystem

| | |
|---|---|
| **Навіщо** | Каталог — це дані + чисті функції над ними, і майже будь-яка зміна в `app/` вимагає бачити обидві половини одночасно. Наприклад: правиш `lowStock()` — треба звірити межу `stock <= reorderLevel` з фактичними значеннями у `data/catalog.json`, інакше не зрозуміло, чи новий фільтр взагалі щось відсіює. Або додаєш тест у `src/catalog.test.ts` — потрібен реальний `sku` і його `price`/`stock`, щоб очікуване число не було вигаданим. Сервер дає агенту прочитати `catalog.json` і `src/` напряму, без копіювання фрагментів у чат: `search_files` знаходить, де використовується конкретна функція, `read_multiple_files` показує `catalog.ts` і `catalog.test.ts` поруч. Для 24 товарів і шести експортованих функцій це різниця між «агент рахує по описі» і «агент рахує по даних». |
| **Транспорт** | stdio |
| **Як запускається** | `npx -y @modelcontextprotocol/server-filesystem@2026.7.10 ./app` |
| **Область доступу (scope)** | Тільки `./app` — відносний шлях від кореня репозиторію, тож конфіг переносний між машинами. **Не** корінь репо, **не** домашня тека, **не** весь диск. Чому цього достатньо: бібліотека каталогу самодостатня — дані (`data/catalog.json`), логіка (`src/`), тести й конфіг збірки лежать в одній теці. Поза scope свідомо залишились `docs/`, `materials/`, `.git/`, `.env` — це документація й метадані репо, а не предметна область, з якою працює сервер. Зокрема, `.env` фізично недосяжний для нього. |
| **Секрети** | Немає — сервер не потребує токена. |
| **Версія** | Зафіксована: `@2026.7.10`. Набір tools цього сервера змінювався між релізами (`read_file` уже позначений deprecated на користь `read_text_file`), тож плаваючий `@latest` означав би, що інструменти можуть змінитись під ногами між сесіями — і поведінка агента разом із ними. |

**Які tools він дав агенту (14, перевірено `tools/list` по stdio):**
`read_file` (deprecated), `read_text_file`, `read_media_file`,
`read_multiple_files`, `write_file`, `edit_file`, `create_directory`,
`list_directory`, `list_directory_with_sizes`, `directory_tree`, `move_file`,
`search_files`, `get_file_info`, `list_allowed_directories`.

> ⚠️ **Цей сервер НЕ read-only.** Чотири з чотирнадцяти tools мають
> `"readOnlyHint": false`, а `write_file`, `edit_file` і `move_file` — ще й
> `"destructiveHint": true`. Тобто в межах `app/` агент технічно може
> перезаписати `data/catalog.json` — файл, який `app/AGENTS.md` забороняє
> редагувати, бо на його числах зав'язані тести й порівняння результатів.
> Вузький scope тут захищає решту диска, але **не** захищає `app/` від самого
> себе. Це усвідомлений прийнятий ризик — детально в
> [`SECURITY.md`](./SECURITY.md).

**Перевірка, що працює:** сервер запущено напряму по stdio (без хоста) —
`initialize` → `notifications/initialized` → `tools/list`. Отримано валідну
JSON-RPC відповідь із 14 tools. У stderr (абсолютний шлях замінено на
`<REPO>` — у вашому виводі там буде шлях до вашої копії репозиторію):

```
Secure MCP Filesystem Server running on stdio
Client does not support MCP Roots, using allowed directories set from server args: [ '<REPO>\\app' ]
```

**Що це означає:** тестовий клієнт оголосив `"capabilities": {}` — без
`roots`. Саме тому спрацював **запасний** механізм: сервер узяв scope з
аргументу командного рядка, і відносний `./app` розв'язався в абсолютний шлях
уже на боці сервера. Якби клієнт підтримував `roots`, цього рядка в stderr не
було б — і реальну область доступу визначав би **хост**, а не аргумент. Тобто
аргумент зі шляхом — не гарантія.

І навіть `roots` гарантією не є: за специфікацією це механізм **координації**,
а не безпеки (сервер *SHOULD* їх поважати, не *MUST*), плюс він позначений
deprecated у ревізії `2026-07-28`. Справжня межа — права ОС, окремий
користувач або пісочниця. Тут такої ізоляції немає: сервер працює під моїм
користувачем і теоретично може все, що можу я — обмежує його лише власна
перевірка шляхів.

| **Навіщо** | У цьому репо є жорсткі домовленості, які не видно з коду й які агент забуває між сесіями: `catalog.json` не можна редагувати; сигнатури експортів у `catalog.ts` заморожені, бо від них залежить `mcp-server/`; `catalog.ts` не має імпортувати `node:*`, щоб лишатись чистим; імпорти йдуть із розширенням `.js` навіть із `.ts`-джерел. ## Сервер 3 — sequential-thinking

| | |
|---|---|
| **Навіщо** | Найдорожча помилка в цьому репо — тиха: агрегація, яка дає правдоподібне, але хибне число. `inventoryValue` — це `sum(price * stock)` із округленням до копійок; `lowStock` — межа `<=`, а не `<`, і сортування за зростанням `stock`. Помилка на одиницю в межі або пропущене округлення не впаде з винятком — воно поверне число, яке виглядає нормально. Такі місця варто проходити покроково з явними проміжними результатами, які можна звірити, а не одним стрибком до відповіді. Той самий інструмент корисний при зміні сигнатури: `catalog.ts` → `index.ts` → `dist/` → `mcp-server/` — ланцюжок, де легко забути ланку. `sequentialthinking` дозволяє ще й переглянути раніший крок, коли на третьому кроці стало ясно, що припущення на першому було хибним. |
| **Транспорт** | stdio |
| **Як запускається** | `npx -y @modelcontextprotocol/server-sequential-thinking@2026.7.4` |
| **Область доступу (scope)** | Немає жодного. Сервер не читає й не пише файли, не ходить у мережу — тримає ланцюжок думок у пам'яті процесу й повертає його назад. |
| **Секрети** | Немає. |
| **Версія** | Зафіксована: `@2026.7.4` — послідовно з рештою набору, щоб оновлення не приходило непомітно разом із `npx`. |

**Які tools він дав агенту (1, перевірено `tools/list`):** `sequentialthinking`.

## Що НЕ підключали і чому

- **`fetch`** — потребує `uvx`, якого в цьому середовищі немає. Але навіть
  якби був: `app/` — бібліотека без жодної runtime-залежності й без мережевих
  викликів, тож зовнішній контент їй нізвідки не потрібен. Натомість сервер
  тягнув би довільний текст з інтернету **прямо в контекст агента** — готовий
  вектор indirect prompt injection. Нульовий виграш за реальний ризик.
- **`git`** — теж `uvx`. Крім залежності: історія цього репо коротка й
  лінійна, а гілки, коміти й diff зручніше робити руками в терміналі, де
  видно, що саме комітиться. Сервер додав би поверхню атаки без виграшу в
  щоденній роботі.
- **`github`** — потребує Personal Access Token. Найвужчий доступний scope
  все одно ширший за реальну потребу («прочитати цей один репозиторій»), а
  токен у контексті агента — це те, що може витекти через prompt injection.
  Робота йде локально, тож віддавати креденшели заради зручності немає сенсу.

## Область доступу — головне

Найважливіший рядок усієї конфігурації — `"./app"` в аргументах
filesystem-сервера. Три висновки, які я з цього виніс:

1. **Scope вужчий за репо, не просто «репо».** `./app`, а не корінь — бо
   `docs/`, `materials/`, `.git/` і `.env` серверу для роботи не потрібні.
   Мінімальні привілеї означають «стільки, скільки треба», а не «стільки,
   скільки зручно».
2. **Аргумент зі шляхом — запасний варіант, не гарантія.** Рядок у stderr
   (`Client does not support MCP Roots...`) з'являється саме тоді, коли
   підтримки `roots` НЕМАЄ. Якщо хост їх підтримує — реальний scope визначає
   він, і моя конфігурація може виявитись не тим, що працює насправді.
3. **Вузький scope ≠ read-only.** У межах `app/` сервер має повний доступ на
   запис, включно з `catalog.json`, який редагувати заборонено. Два різні
   виміри привілеїв — «де» і «що» — і звуження одного нічого не каже про
   інший.
